# Story integration

The story cannot hold logic, so everything it asks for lands in Rust: a command it calls
by name, a hook that runs at a moment in the flow, and the state both of them read.

## Commands

`call <name> <args...>` runs the handler registered under that name. `#[command]` marks
the handler: the parameters after the context are the story's arguments, parsed and
checked for you, and the function's own name is the name the story calls it by.

```story
call give_item verlaine_letter
call give_item candle 3
```

```rust
#[command]
fn give_item(ctx: &mut GameContext, item: String, count: Option<u32>) -> Option<ScreenState> {
    ctx.state.get_mut::<Inventory>().add(&item, count.unwrap_or(1));
    None
}

VnApp::new("My Novel").command(give_item)
```

Because the macro turns the function into the marker the builder takes, nothing repeats
the name and a typo is a compile error rather than an unknown command at startup.
`#[command("note")]` registers a different name than the function's own, and
`name::call(ctx, ...)` runs the handler straight from Rust.

`command_as(name, handler)` is the way in for a closure, or for a name worked out at
runtime:

```rust
VnApp::new("My Novel").command_as("slam", |ctx, ()| { ctx.shake(0.4); None })
```

| Rust type | Accepts |
| --- | --- |
| `String` | any word |
| A `#[derive(StoryWord)]` enum | one of its words, checked by `novn check` |
| `i8`…`i64` | an integer |
| `u8`…`u64`, `usize` | a non-negative integer |
| `f32`, `f64` | a number |
| `bool` | `true` / `false` |
| `Option<T>` | an optional trailing argument |
| `()` | no arguments |
| `Vec<String>` | any number of words, unchecked |

A command takes up to five arguments, and required ones have to come before optional ones,
which is checked when the command is registered. The signature is part of the schema, so
every `call` in the story is checked at startup for argument count and kind, and again
when it runs.

Returning `Some(state)` switches screens, to a text input for instance; the story resumes
from the next instruction when the playing screen comes back.

## Words the story may write

An argument drawn from a fixed set, an item or an ending or a room, is an enum, and
`#[derive(StoryWord)]` makes it a type the engine can parse.

```rust
#[derive(StoryWord, Clone, Copy, PartialEq, Eq)]
enum Ending { Report, Silence, Keeper }

#[command]
fn close_case(ctx: &mut GameContext, ending: Ending) -> Option<ScreenState> {
    ctx.persistent.get_mut::<CaseLedger>().close(ending);
    None
}
```

Variant names become the words: `EndingKeeper` is `ending_keeper`, `Folio41` is
`folio_41`, and `#[word("...")]` names the odd one out. The set travels into the signature,
and because signatures are exported to `schema.json`, `novn check` catches a word outside
the set before the game runs, the way it already catches an unknown scene or image.

```text
02_notebook.story:80: error: `call note` argument 1 should be one of debt_paid, folio_41,
hot_water, got `folio41`; did you mean 'folio_41'?
```

The LSP offers the same words while a `call` line is being typed. The derive also writes
`as_str`, `from_word`, `ALL`, `Display` and serde impls that read and write the word
itself, so the story, the save file and `novn check` all speak the same string, and a save
holding a word the game no longer has says so instead of loading something wrong.

## Hooks

Hooks run Rust at points in the story without a `call` in the script.

```rust
VnApp::new("My Novel")
    .on_scene_enter(|ctx, scene| {
        ctx.state.get_mut::<Journal>().visited(scene);
        None
    })
    .on_choice(|ctx, index, text| {
        println!("picked option {} ({})", index, text);
        None
    })
```

| Hook | Runs |
| --- | --- |
| `on_scene_enter` | When the story enters a scene: at the start, on every `jump` including one to the same scene, and when a load or a hot reload restarts an edited scene. Not when a save or a rollback puts the story back into the middle of a scene |
| `on_choice` | Right after the player picks, before the option's lines run. `text` is the option as shown, and `index` is its place in the story's `choice:` block, so an option hidden by a `when` does not shift the ones after it |
| `on_frame` | Every frame the playing screen updates, after the story has advanced and before the characters are drawn. It returns nothing: a hook running sixty times a second is a place to push a value, not to change screens |

Hooks are registered in order and all of them run. Like commands, returning `Some(state)`
switches screens and the first one returned wins. They see the same `GameContext` commands
do.

Rolling back and playing forward again runs them again, so a hook with a permanent effect,
an achievement say, should check whether it already happened, or the story should `commit`
first.

## Game state

State owned by Rust, an inventory or a set of relationships, is registered by type and
reached from any screen, overlay or command.

```rust
#[derive(Clone, Default, Serialize, Deserialize)]
struct Inventory { /* ... */ }

VnApp::new("My Novel").state(Inventory::default())

ctx.state.get_mut::<Inventory>()   // in update, and in commands
ctx.state.get::<Inventory>()       // in draw
```

State types derive `Serialize` and `Deserialize` because they are saved with the game.
`get` and `get_mut` panic with the type name if it was never registered; `try_get` and
`try_get_mut` hand back an `Option` instead. `Action::NewGame` resets every registered
value to the one passed to `state()`, which is what the `Clone` is for.

Story variables are not here. Those live in the VM, reachable through
`ctx.story.variables()`.

## Hot reload

In debug builds, editing a `.story` file while the game runs reloads the story without
restarting. Every half second the engine checks modification times under `story_dir`, along
with files added and removed. The new story is validated exactly as at startup, and then
the player's position moves into it the way loading a save does.

| Change | Result |
| --- | --- |
| Other scenes | The same line stays on screen, and rollback history in unchanged scenes is kept |
| The current scene | It restarts from its top, keeping variables, characters and game state; rollback history is cleared |
| The current scene was deleted | Nothing changes, and the error arrives as a notification |
| Errors anywhere | Nothing changes: the game keeps running the previous story, and the diagnostics go to the console and to a red panel at the top of the window |

The error panel lists every diagnostic as `file:line: error: message`, with paths relative
to the story directory, under "Story not reloaded: N errors (still running the previous
version)". It stays until a reload succeeds, and F2 collapses it to its title and back.

`.hot_reload(false)` turns it off, and `.hot_reload(true)` turns it on in release builds
too. The rest of what a debug build carries is on the [dev tools](/docs/engine/dev-tools) page.
